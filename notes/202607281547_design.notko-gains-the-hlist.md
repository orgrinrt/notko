## What notko gains: `notko-hlist`

A new crate in the notko repository holding the heterogeneous type-level list that three repositories
have now independently reinvented.

**The duplication that prompted it**, with citations:

- `hilavitkutin/mock/crates/hilavitkutin-api/src/access.rs:50` declares `pub struct Empty;` and
  `pub struct Cons<H, T>(core::marker::PhantomData<(H, T)>);`
- `kolli/mock/crates/kolli-api/src/lib.rs:143` declares the same two, byte-identical.
- arvo was about to declare a third, for the shape system.

Each has since regrown the same operations under different names. hilavitkutin has `AccessSet` (a
length fold), `Contains`, `ContainsAll` and `Concat`. kolli has `CommandSet` with `LEN`, `each` and
`find`.

## The surface

```rust
pub struct Empty;
pub struct Cons<H, T>(core::marker::PhantomData<(H, T)>);

pub trait Cardinal { const ZERO: Self; fn succ(self) -> Self; }
pub trait Length<N: Cardinal> { const LEN: N; }
impl<N: Cardinal, H, T: Length<N>> Length<N> for Cons<H, T> { const LEN: N = T::LEN.succ(); }

pub trait Contains<X> { }        // #[marker], head match + recursive tail match
pub trait ContainsAll<L> { }     // #[marker], base + recursive
pub trait Concat<L> { type Out; }
```

The membership and concatenation traits come straight from hilavitkutin's version, including its
`#[diagnostic::on_unimplemented]` messages and the `recursion_limit = "1024"` hint, which are the part
that makes the errors survivable.

## Why the count is parameterised rather than fixed or dropped

notko cannot name arvo's `USize`, since arvo depends on notko. Two shapes were considered and one is
impossible:

**A separate counting crate in arvo is blocked by the orphan rule.** If notko declares both the trait
and the list types, an impl in arvo has two foreign items and cannot be written. Only notko can
implement a notko trait for notko types.

**So the count parameterises in notko**, and each consumer implements `Cardinal` for its own type,
which is legal because the type is theirs: `impl Cardinal for USize` lives in arvo, trait foreign,
type local. One crate rather than two, and the count type stays the consumer's choice.

The cost is that the successor must be const-callable, so `Cardinal` is a const trait and notko gates
`const_trait_impl`, as arvo already does.

## Naming

**`Cardinal`, not `Countable` and not `Natural`.** `-able` means "can be counted", and this type **is**
the count, so the suffix inverts the meaning. `Natural` is exactly precise, since zero and successor
are the Peano constructors, and that is the problem: it claims a mathematical primitive, which is
arvo's territory. notko's traits are properties, `Boundable` and `NonZeroable`, and `Cardinal` joins
that family. It also leaves `Natural` free for arvo.

**The crate is `notko-hlist`.** The workspace vocabulary rule was reversed on 2026-07-28 to prefer
`hlist` over `cons-list`: `HList` is the established term for a heterogeneous type-level list, from
Kiselyov, Lämmel and Schupke onward, where `cons-list` is Lisp lineage that says nothing about
heterogeneity and in Rust names the book's runtime linked list instead.

## What notko does not gain

**Not monoids.** Semantically that is numerics and mathematics territory, and it lands in
`arvo-algebra-contracts`. An earlier argument that the fold needs the monoid and so the monoid should
follow the fold into notko was rejected: folding may be notko's, the algebra is not.

The consequence is worth stating so it is not rediscovered: `notko-hlist` can offer the **structural**
folds, which need no algebra, being `Length`, `Concat` and `ContainsAll`. A **value-level** fold that
reduces with an identity and an associative combine needs the algebra, so it belongs where the algebra
is.

## How consumers take it

Each aliases the cell and the leaf to its own vocabulary, so the generic names appear at the
definition and almost nowhere else:

| Consumer | Cell | Leaf |
|---|---|---|
| arvo shape | `Axis<H, T>` | `Scalar` |
| hilavitkutin | `Access<H, T>` | `Deny`, provisional |
| kolli | `Command<H, T>` | `EmptyInvoke`, provisional |

Rank 0 being `Scalar` is not a pun: a shape with no axes is a scalar.
