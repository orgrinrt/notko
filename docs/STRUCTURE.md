### build

`notko-build` · depth 0

[![Crates.io](https://img.shields.io/crates/v/notko-build)](https://crates.io/crates/notko-build) [![docs.rs](https://img.shields.io/docsrs/notko-build)](https://docs.rs/notko-build)

> The build-script half of `#[profile]`'s custom tiers. Gathers one directory for the proc-macro to read, from a crate and whichever of its direct dependencies opted in.

Custom tiers are ordinary files a crate keeps in its own `notko-optimisers/` directory, and by default the [`notko-macros`](https://crates.io/crates/notko-macros) proc-macro only sees the ones belonging to the crate it's expanding into. This build-script helper is for the case where a tier is defined in one crate and used in another. It copies the crate's own optimiser files and the ones its dependencies handed over into `$OUT_DIR/notko-optimisers/`, and points the proc-macro at the result through `NOTKO_OPTIMISERS_PATH`.

##### Usage

```bash
cargo add --build notko-build
```

```toml
[build-dependencies]
notko-build = "0.0.1"
```

A crate that only uses tiers from its dependencies calls it from its `build.rs`, and calling it on every build is the intended shape. It returns an error anywhere that isn't a build script.

```rust
// build.rs
fn main() -> Result<(), Box<dyn std::error::Error>> {
    notko_build::collect_and_distribute()?;
    Ok(())
}
```

A crate that provides tiers declares `links` with any value that's unique in the graph, since that's what makes cargo carry the metadata to its dependents, and keeps its tiers in `./notko-optimisers/*.rs`. Each file needs the marker line and a `based_on`, and the other two keys are optional:

```rust
//! @notko-optimiser
//! based_on = "Hot"
//! inline = true
//! panic_fmt = "trace invariant violated: {err:?}"
```

The file's stem is the tier's name, so `Trace.rs` is what `#[profile(Trace)]` looks for, and the full key list is in the [`notko-macros`](https://crates.io/crates/notko-macros) readme. Two dependencies providing the same tier name is a build error naming both, and a file in the crate's own directory wins over every dependency's.

The `DEP_*` variables only reach a crate's direct dependencies, and only the ones that declare `links` and run this themselves, so a tier two hops away arrives only if the crate in between forwards it. The pieces have tests, but the whole cargo handshake hasn't been run end to end here.

### hlist

`notko-hlist` · depth 0

[![Crates.io](https://img.shields.io/crates/v/notko-hlist)](https://crates.io/crates/notko-hlist) [![docs.rs](https://img.shields.io/docsrs/notko-hlist)](https://docs.rs/notko-hlist)

> A heterogeneous type-level list, and the structural facts about one. Length in a count type of the consumer's own, membership, position, append, and a product of values over the list, all decided by the compiler.

A list here is `Empty`, or `Cons<H, T>` where the tail is itself a list, and neither exists at run time: both are zero-sized markers, and everything the crate says about a list it says through traits the compiler discharges. So `Cons<Db, Cons<Cache, Empty>>` can be a set of things a function is allowed to touch, and a bound like `L: Contains<Db>` is the compiler agreeing before anything runs. `At<P>` says which type sits at a place, written as `Here` or `There<P>` and read back as a number through `Position`, and `PlaceOf<M, P>` goes the other way, from a member to its place with the place inferred.

The list itself holds nothing, so `Project<C>` gives it a product through a carrier `C`: one value per member, or a column, or an array, with a member naming its value type through `Elem`, or a form the carrier states for each member on its own, a value for one and a borrow for the next. The carrier is a type and states one form per member, and the product's type names the carrier and every member, so nothing about what a field holds is left to inference. `Has` reaches one member's field of it, `SubOf` cuts a narrower list's product out of a wider one, and the operations on a whole product write in place, so a long list does not cost a stack frame per member holding the rest of it.

It stays small otherwise, with nothing that needs algebra. The count is a parameter of the traits, so the length comes back in whatever type the consumer already counts with. The `List` trait is sealed, so a type of your own can't claim to hold something, and `L: Contains<Db>` really proves `Db` is in there.

It has no dependencies, and it's pre-1.0 so the trait names may still move. The two features, `const` and `membership`, are both on by default and both need nightly. With them off it builds on stable from 1.85, minus `Contains`, `ContainsAll` and the const paths, and the product operations are then ordinary calls rather than ones a constant can make.

##### Usage

```bash
cargo add notko-hlist
```

```toml
[dependencies]
notko-hlist = "0.0.1"
```

On stable, turn the defaults off:

```toml
[dependencies]
notko-hlist = { version = "0.0.1", default-features = false }
```

##### Example


```rust
// The default set needs nightly, and this is where that gets said.
####![feature(const_trait_impl)]

use notko_hlist::{At, Cardinal, Concat, Cons, Contains, ContainsAll, Empty, Here, Length, Position, There};

// The names are meant to appear at the definition and almost nowhere else, so
// alias them into whatever the thing actually is.
type NoStores = Empty;
type Store<H, T> = Cons<H, T>;

struct Db;
struct Cache;
struct Log;

type Reads = Store<Db, Store<Cache, NoStores>>;
type Writes = Store<Log, NoStores>;

// The count is the consumer's type, not one this crate picked. Implement the two Peano
// constructors on it and every list has a length in it.
####[derive(Clone, Copy, PartialEq, Debug)]
struct Count(usize);

const impl Cardinal for Count {
    const ZERO: Self = Count(0);
    fn succ(self) -> Self {
        Count(self.0 + 1)
    }
}

// Resolved by the compiler, so this is a constant and not a walk.
const READS: Count = <Reads as Length<Count>>::LEN;

// Composition: a unit declaring both sets ends up with everything either had.
type Touched = <Reads as Concat<Writes>>::Out;

// Position, where the depth is the question rather than something to hide.
// `Cache` is the second store read, and the index is what gets handed to a run of
// values sitting beside the list.
type Second = There<Here>;
const SECOND: Count = <Second as Position<Count>>::INDEX;

// And the bound a caller actually writes. `Touched` holding `Log` is checked
// here, and passing a set that does not is a compile error rather than a
// lookup that fails later.
fn runs_against<Set: Contains<Log> + ContainsAll<Reads>>() {}

// The member at a position, named in the signature. Handed the wrong position
// this does not compile, which is the whole reason to index this way.
fn second_store<L: At<Second, Member = M>, M>(value: M) -> M {
    let _ = core::marker::PhantomData::<L>;
    value
}

fn main() {
    assert_eq!(READS, Count(2));
    assert_eq!(SECOND, Count(1));
    runs_against::<Touched>();
    let _: Cache = second_store::<Reads, Cache>(Cache);
}
```

### macros-core

`notko-macros-core` · depth 0

[![Crates.io](https://img.shields.io/crates/v/notko-macros-core)](https://crates.io/crates/notko-macros-core) [![docs.rs](https://img.shields.io/docsrs/notko-macros-core)](https://docs.rs/notko-macros-core)

> The AST rewriting behind `#[profile(Tier)]`, as an ordinary library. Ships `tiers`, `parse`, `discover` and `rewrite`, which is what another crate's fallibility-tier attribute would build on.

A proc-macro crate can't export anything that isn't a macro, so the rewrite engine that [`notko-macros`](https://crates.io/crates/notko-macros) runs on lives here as an ordinary library, and an attribute of another crate's own can build on it instead of doing the rewriting again. It holds the rewrite engine, the tier vocabulary it rewrites against and the discovery that turns a tier name into something to rewrite with, and the full surface is on [docs.rs](https://docs.rs/notko-macros-core).

##### Usage

```bash
cargo add notko-macros-core
```

A rewrite has to name some crate for the type it produces, and a gate feature for the release arm, and both belong to the calling crate rather than to this one. So the library takes them as fields and defaults to nothing you'd want:

```rust
// my-macros/src/lib.rs
use notko_macros_core::tiers::{CustomTier, Hot};
use proc_macro::TokenStream;

####[proc_macro_attribute]
pub fn profile_asserted(_attr: TokenStream, item: TokenStream) -> TokenStream {
    // one tier, built by hand
    let input = match syn::parse::<syn::ItemFn>(item) {
        Ok(f) => f,
        Err(e) => return e.to_compile_error().into(),
    };
    // both the crate and the gate feature belong to the calling crate, not this one
    let mut tier = CustomTier::from_marker::<Hot>()
        .with_crate(syn::parse_quote!(::my_runtime))
        .with_gate_feature("my_release_arm");
    tier.panic_fmt = Some("asserted invariant violated: {err:?}".into());
    notko_macros_core::rewrite::rewrite_fn(tier, input)
        .unwrap_or_else(|e| e.to_compile_error())
        .into()
}
```

`Discovery` is the same lookup notko's own macro runs, with every name in it the calling crate's. Every field is named rather than spread over `Discovery::default()`, which is notko's own and would emit code naming `notko` in consumers that never depended on it:

```rust
use notko_macros_core::discover::Discovery;

fn mine() -> Discovery {
    Discovery {
        krate: syn::parse_quote!(::my_runtime),
        gate_feature: "my_release_arm".to_string(),
        dir: "my-tiers".to_string(),
        env_var: "MY_TIERS_PATH".to_string(),
        marker: "@my-tier".to_string(),
        docs: "the my-macros readme".to_string(),
    }
}

// then, in the attribute:
let tier = mine().resolve(&name, span)?;
```

The surface moves with the rest of the crates, and on a `0.0.x` version cargo resolves to exactly that one, so what `cargo add` writes is already the pin.

### macros

`notko-macros` · depth 1

[![Crates.io](https://img.shields.io/crates/v/notko-macros)](https://crates.io/crates/notko-macros) [![docs.rs](https://img.shields.io/docsrs/notko-macros)](https://docs.rs/notko-macros)

> An attribute macro that rewrites a `Result` function to one of `notko`'s three fallibility tiers. Ships `Hot`, `Warm` and `Cold`, and reads custom tiers from a file.

The `#[profile]` attribute takes an ordinary `Result` function and rewrites both its signature and its body into the tier named on the tag, so the choice sits in one place instead of in every type spelled out inside the function. The tiers themselves live in [`notko`](https://crates.io/crates/notko), which is what the rewritten body names, so that belongs in the dependencies as well.

##### Usage

```bash
cargo add notko-macros
```

Or reach it through `notko`, which re-exports `#[profile]` under the `macros` feature:

```bash
cargo add notko --features macros
```

That leaves `notko`'s defaults on, which want a nightly compiler. On stable it's `cargo add notko --no-default-features --features macros`.

##### Example

```rust
use notko_macros::profile;

####[derive(Debug)]
pub struct LookupErr;

####[profile(Hot)]
pub fn lookup(id: u32) -> Result<u32, LookupErr> {
    Ok(id.wrapping_mul(2))
}

####[derive(Debug)]
pub struct SetupErr;

####[profile(Cold)]
pub fn init(retries: u32) -> Result<u32, SetupErr> {
    if retries == 0 {
        return Err(SetupErr);
    }
    Ok(retries)
}
```

`Hot` becomes `Outcome<T, E>` in debug builds and `Just<T>` in a release build with the consumer's own `internal` feature on, where `Err` and a failing `?` turn into a panic, and an abort under `panic = "abort"`. Hot is for code that does not branch and does not fail, taken as an extra optimisation where that is true, and the panic is what it does when that promise turns out wrong. The debug arm hands the error back so a test can see it, but the two arms only agree on code that never fails, and code that can fail belongs on `Cold` or `Warm`. `Cold` is always `Outcome<T, E>`, and `Warm` is always `Maybe<T>` with the whole `Err(..)` expression dropped, side effects included. The `internal` feature has to be declared in the consuming crate, with `internal = []` under `[features]`, since the `cfg` is read where the attribute expands. Without it everything still compiles on the `Outcome` arm, but each hot `#[profile]` warns.

The rewrite only fires on a return type spelled `Result<T, E>` or `Outcome<T, E>` with both arguments written out. Anything else, like a `Result<T>` alias, is emitted as written without an error, so writing the two arguments out is the fix when a tag seems to do nothing.

Custom tiers are a file at `notko-optimisers/<Name>.rs` in the consuming crate, with the same shape as above: `//! @notko-optimiser`, then `based_on` (one of `Hot`, `Warm` or `Cold`, case-sensitive), and optionally `inline` and `panic_fmt`, the second read on the hot strategy only. `#[profile(Trace)]` then looks for `Trace.rs`. [`notko-build`](https://crates.io/crates/notko-build) fills a third source for tiers shared between crates, and [`notko-macros-core`](https://crates.io/crates/notko-macros-core) has the pieces for writing a separate attribute of your own.
